# Git 規約

## コミットメッセージ

### フォーマット

```
<type>: <subject（日本語）>

<章タイトル>:
* ファイル名.java: 実装内容の説明
* ファイル名.java: 実装内容の説明

<章タイトル>:
* ファイル名.java: 実装内容の説明
```

- **1行目**: `<type>: <subject>` 形式。type は変更の主目的で選び、subject は日本語で記載する
- **2行目**: 必ず空行にする
- **3行目以降**: 章立てし、各章の直下に `*` で始まる箇条書きで実装内容を列挙する
- **スコープは使用しない**（`feat(auth):` のような記法は禁止）

> 2行目の空行は `gh pr create --fill` が subject を PR タイトル、3行目以降を PR 本文として自動認識するために必要。

### prefix 一覧

| prefix     | 用途                         |
|------------|----------------------------|
| `feat`     | 新機能の追加                     |
| `fix`      | バグ修正                       |
| `docs`     | ドキュメントのみの変更                |
| `test`     | テストの追加・修正（プロダクションコードの変更なし） |
| `refactor` | バグ修正・機能追加を伴わないコード変更        |
| `chore`    | ビルド設定・依存関係・CI など雑務         |
| `style`    | コードスタイルのみの変更（ロジック変更なし）     |
| `perf`     | パフォーマンス改善                  |

### 章一覧

コミット本文は以下の章で構成する。レビュー時に注視すべき箇所（FEAT / FIX）と、そうでない箇所（STUBS / レビュー不要）を分離し、レビュー負荷を減らすことが目的。

| 章          | 用途                                                       |
|------------|----------------------------------------------------------|
| `FEAT`     | 完成した機能の追加                                                |
| `FIX`      | バグ修正、および FEAT / FIX の影響で修正した箇所                           |
| `REFACTOR` | リファクタリング目的の修正                                            |
| `STUBS`    | スタブとして実装したもの（後続作業で完成・置換する前提の一時実装。宣言のみのポート、DI 解決用スタブなど）   |
| `DOCS`     | `docs/` 配下などレビュー対象ドキュメントの修正                              |
| `CHORE`    | ビルド設定・依存関係・CI・整形のみなどの雑務的変更                               |
| `レビュー不要`   | `TODO.md` や `.steering/` 配下など、過程公開のために git 管理しているだけのファイル |

- 章は上表の順（FEAT → FIX → REFACTOR → STUBS → DOCS → CHORE → レビュー不要）で記載し、該当ファイルのない章は省略する
- テストコードは対象機能と同じ章に記載する（TEST 章は設けない）。テスト単独コミット（`test:`）でも、対象コードが属する章（通常 FEAT）を用いる。レビュー対象であることが即座にわかるようにするため
- 同一ファイルが複数章に該当する場合、スタブ実装であれば STUBS を優先する（例: インターフェース変更へのコンパイル追随をスタブで行った場合は FIX ではなく STUBS）
- `.steering/` 配下のドキュメントは「レビュー不要」章に記載する。形式は `* .steering/: 上記作業のステアリングドキュメントを追加`

### サンプル

```
feat: refresh エンドポイント(application 層)を追加

FEAT:
* AuthService.java: refresh ユースケースを実装（ハッシュ検索 → 有効性検証 → ローテーション → アクセストークン再発行）
* ClockConfig.java: 有効期限判定のテスト容易性のための Clock Bean 定義を追加
* AuthServiceTest.java: refresh の正常系 1 件・異常系 6 件のテストを追加

STUBS:
* RefreshToken.java: リフレッシュトークン集約のスタブを追加（データ保持のみ。期限切れ・失効判定と revoke は後続）
* RefreshTokenRepository.java: ハッシュ検索・保存ポートの宣言を追加（実装は後続）
* StubRefreshTokenRepository.java: DI 解決用の一時スタブ実装を追加（@SpringBootTest のコンテキスト起動用。置換は後続）

レビュー不要:
* TODO.md: 上記スタブを各層の章へ登録し、AuthService#refresh(RefreshCommand) を完了に更新
* .steering/: 上記作業のステアリングドキュメントを追加
```
